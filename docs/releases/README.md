# リリースの案内

GitHub Releases に載せるリリースの案内を、版ごとに `v<アプリの版>.md` で置く。タグを打つと、公開ワークフロー（`Publish-Package.yml`）がこのファイルをそのままリリースの本文にする。手順は [バージョンの管理](../versioning.md) の「リリース」、作業は `.claude/skills/release/SKILL.md`（スキル `release`）にまとめている。

| ファイル | 内容 |
|---|---|
| `template.md` | 新しい版の案内のひな形。`tools/release.py bump` が `{app}`・`{library}`・`{changes}` を埋めて `v<版>.md` を作る |
| `v3.5.1.md` 〜 | 出した版の案内。v3.5.4 までは GitHub Releases の本文を写したもの |

`tools/release.py check` は、いまの版の案内があり、書きかけ（`<!-- TODO`）が残っていないことを確かめる。CI（`release-check`）とタグの公開（`check-version`）で動く。

## 書き方

読むのは、遊ぶ人・シナリオを作る人・SRC#Web を自分のサイトに置く人。開発の経緯ではなく、使う人から見て何が変わったかを書く。

- **冒頭**: 版の 1 文のあとに、今回の要点を 1〜3 文で書く。
- **遊ぶ**: 入手先の表。ひな形のまま使い、入手先が変わったときだけ直す。
- **動きが変わる点**: 既存のシナリオ・セーブデータ・設定で、見え方や結果が変わるものを書く。元の SRC に合わせた修正でも、SRC# の前の版で作ったシナリオに効くものはここに書く。どう書き直せば前と同じになるか（例: ClearPicture を使う）も書く。無ければ節ごと消す。
- **主な変更**: 太字の見出しで分ける。目安の順は、目玉の機能 → 不具合の修正 → フロントエンドごと（SRC#Web・SRC#Avalonia・SRC#Form・データビューア）→ 作成支援（srcsharp・VS Code 拡張・lint）→ その他。
  - 1 項目は、何ができるようになったか・何を直したかを 1〜2 文で。末尾に PR の番号を `（#1234）` で付ける。
  - 不具合は「〜していたのを直しました」と、起きていたことを書く。クラス名・メソッド名など中の名前は書かない。コマンド・設定・ファイル名・URL のパラメーターなど、使う人が書くものはそのまま書く。
  - 数字で言えるもの（速さ・大きさ）は前後の値を書く。
  - CI・文書・依存パッケージの更新は「その他」にまとめ、PR の番号を並べる。
- **パッケージ**: ひな形のまま（版は `bump` が埋める）。
- 文体は「です・ます」。用語は [SRC# のヘルプ](https://srch.7474.jp/) とこのリポジトリの文書に合わせる（例: 「特殊能力」「マップコマンド」「共有パック」）。

## 下書き

`tools/release.py changes` は、前のタグから master までの PR を、変えたファイルの多い分野ごとに並べる。Dependabot の PR は「依存パッケージの更新」に番号だけ並べる。PR の題をそのまま並べただけなので、PR の説明とコミットを読んで、上の書き方で書き直す。
